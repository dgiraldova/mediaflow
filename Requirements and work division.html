MVP 1 Implementation Plan

AI-Native Searchable Media Library

Document status: Ready for implementation
Team size: 3 technical contributors
Primary objective: Turn unorganized business videos and images into a searchable library of timestamped marketing moments
Architecture: Modular monolith with asynchronous media workers
Initial integrations: Direct upload and Google Drive
Primary users: Marketing teams, content agencies and companies producing recurring media


1. Product vision

Businesses continuously produce:

  • Founder recordings
  • Customer interviews
  • Product demonstrations
  • Podcasts
  • Webinars
  • Event footage
  • Social-media videos
  • Product photography
  • General B-roll

Most of this media is stored in folders without consistent names, tags or descriptions. Valuable material becomes effectively invisible after a few weeks.

The product will connect to an existing media source, analyze its contents automatically and allow users to find exact moments through natural-language queries.

Example:

Find the moment where a customer says implementation was easier than expected.

The result should open the correct video at the relevant timestamp rather than returning only the full recording.

The MVP must demonstrate that a company can connect or upload an unorganized media library and recover useful moments without manually organizing every file.


2. MVP product promise

A user should be able to:

  1. Create an account and organization.
  2. Upload a video or connect a Google Drive folder.
  3. See the ingestion and analysis status.
  4. Search the library using natural language.
  5. Receive exact video segments relevant to the query.
  6. Open a result at the matching timestamp.
  7. Inspect its transcript and AI-generated description.
  8. Add useful moments to a collection.
  9. Select and export a basic clip.
  10. Keep every organization’s content isolated and secure.

The MVP is successful when a user can take a disorganized set of recordings and recover a specific useful moment without knowing:

  • The filename
  • The folder
  • The recording date
  • The speaker’s exact words
  • The exact timestamp


3. Non-goals

The following are explicitly outside MVP 1:

  • Social-media publishing
  • Meta Ads integration
  • Campaign-performance analytics
  • Automatic vertical reframing
  • Branded video templates
  • Advanced video editing
  • Collaborative annotations on individual frames
  • Formal rights-management workflows
  • Model-release document management
  • Face recognition
  • Custom model training
  • Automated content recommendations
  • Generative social-media copy
  • Mobile applications
  • Native desktop applications
  • Enterprise SSO
  • On-premise deployment
  • Real-time livestream indexing
  • Full digital-asset-management replacement
  • Automatic deletion or reorganization of source files

These capabilities may be supported architecturally, but they must not delay MVP 1.


4. MVP success criteria

4.1 Functional success

A test organization must be able to index at least:

  • 100 video files
  • 20 hours of total video
  • Mixed English and Spanish speech
  • Videos with inconsistent filenames
  • Videos from direct upload and Google Drive

The user must then be able to:

  • Search using natural language
  • Receive timestamped results
  • Filter by source, date and media type
  • Open a matching result at the correct point
  • Add a result to a collection
  • Export a selected section as a new clip

4.2 Search-quality target

For a curated evaluation set of at least 40 queries:

  • Relevant moment appears in the first 5 results for at least 75% of queries.
  • Exact quoted speech appears in the first 3 results for at least 90% of queries.
  • No result from another organization is ever returned.
  • Each result includes an explanation of why it matched.

These numbers are product targets, not contractual guarantees.

4.3 Operational target

  • Failed ingestion jobs can be retried.
  • Duplicate uploads are detected.
  • Processing can resume after worker interruption.
  • Every pipeline stage exposes its status.
  • Reprocessing does not create duplicate moments.
  • Errors are visible to both developers and users.
  • Secrets are never stored in the frontend bundle.
  • Large uploads do not pass through Vercel functions.

6. Architecture principles

6.1 Start as a modular monolith

The backend should be deployed as:

  1. One FastAPI application
  2. One Temporal worker application
  3. One media-processing worker image
  4. One Next.js application

Do not create independent microservices for every module.

Modules must have clean boundaries, but may initially share:

  • One repository
  • One Postgres database
  • One deployment pipeline
  • One Python package
  • One internal domain model

6.2 Own the canonical data

External AI-provider indexes are not the source of truth.

The application database must own:

  • Organizations
  • Assets
  • Source-file references
  • Processing status
  • Transcripts
  • Moments
  • AI annotations
  • Collections
  • Clip definitions
  • Search history
  • Provider identifiers
  • User corrections
  • Pipeline versions

6.3 Operate on media moments

The main searchable unit is not a complete video. It is a timestamped media_moment.

A moment contains:

  • Asset ID
  • Start timestamp
  • End timestamp
  • Transcript
  • Visual description
  • Marketing description
  • Content classifications
  • Technical information
  • Search embedding
  • Provider references
  • Analysis version

6.4 Keep provider integrations replaceable

The domain layer must not depend directly on Twelve Labs, OpenAI or any specific vendor.

Use provider interfaces and adapters.

6.5 Make ingestion idempotent

Running the same operation twice must not create duplicate:

  • Assets
  • Transcripts
  • Moments
  • Provider jobs
  • Thumbnails
  • Proxies
  • Search documents

Use checksums, idempotency keys and database uniqueness constraints.

6.6 Security is part of the schema

Every tenant-owned table must include organization_id.

RLS policies must prevent users from reading or modifying data outside their organizations.

The Supabase service-role credential must exist only in trusted backend environments and must never be exposed in the browser. Supabase explicitly warns that service credentials bypass RLS and should not be shared with clients.

10.3 RLS policy rule

For every organization-owned row:

A signed-in user may access the row only when an

organization_members row exists linking that user to the row’s organization.

Write automated database tests for:

  • User in Organization A cannot read Organization B.
  • User in Organization A cannot insert data for Organization B.
  • Viewer cannot delete assets.
  • Member cannot manage organization membership.
  • Backend service operations can process authorized assets.


11. Media ingestion pipeline

11.1 Direct-upload flow

1. User requests an upload.

2. API creates an asset in uploading state.

3. API returns a presigned multipart-upload URL.

4. Browser uploads directly to R2.

5. Browser reports upload completion.

6. API verifies object metadata.

7. API calculates or verifies checksum.

8. API changes asset to queued.

9. API starts Temporal ingestion workflow.

10. Worker processes media.

11. Asset becomes ready or failed.

The original media must not pass through the Next.js server or FastAPI process.

11.2 Google Drive flow

1. User authorizes Google Drive access.

2. User selects one or more folders.

3. Connection stores encrypted refresh credentials.

4. Initial sync discovers supported media files.

5. Each discovered file becomes an asset.

6. Duplicate source IDs and checksums are ignored.

7. Eligible files start an ingestion workflow.

8. Incremental sync checks for new or modified files.

For MVP 1, Google Drive synchronization may be pull-based:

  • Manual “Sync now”
  • Scheduled synchronization every 15 minutes

Webhooks can be added later.

11.5 Retry behavior

Recommended defaults:

  • Network activity: exponential backoff, maximum 5 attempts
  • AI-provider rate limit: exponential backoff with jitter
  • Invalid media: no automatic retry
  • Corrupted source: no automatic retry
  • Worker termination: workflow resumes
  • Temporary storage failure: retry
  • Authentication expiry: pause and mark connection as requiring attention


12. Media processing specifications

12.1 Supported video formats

Initial support:

  • MP4
  • MOV
  • WebM
  • M4V

Reject unsupported files with a clear user-facing explanation.

12.2 Proxy specification

Generate a standard playback proxy:

Container: MP4

Video codec: H.264

Audio codec: AAC

Maximum width: 1280

Frame rate: preserve up to 30 FPS

Fast-start enabled

Do not replace the original.

12.3 Thumbnail specification

Generate:

  • Main thumbnail
  • Several evenly spaced preview thumbnails
  • Optional contact sheet

Suggested main-thumbnail selection:

  1. Exclude very dark frames.
  2. Exclude blurred frames where possible.
  3. Prefer a frame with a visible person or product.
  4. Fall back to a frame around 20% of the duration.

12.4 Clip export

MVP clip export accepts:

  • Source asset
  • Start timestamp
  • End timestamp

Initial restrictions:

  • Maximum clip length: 5 minutes
  • Preserve source aspect ratio
  • MP4 H.264 output
  • No captions burned in
  • No music
  • No reframing
  • No transitions

Use accurate cuts, even when re-encoding is necessary.

14. Moment-generation strategy

Do not depend on one segmentation method.

Create moment candidates from:

  1. Transcript boundaries
  2. Speaker changes
  3. Silence boundaries
  4. Video-provider search segments
  5. Visual scene changes
  6. Maximum segment length

14.1 Initial segment rules

  • Minimum moment length: 3 seconds
  • Preferred moment length: 10–45 seconds
  • Maximum semantic moment length: 90 seconds
  • Merge adjacent transcript segments when they express one idea
  • Split segments that contain multiple unrelated topics
  • Allow overlapping moments when useful

14.2 Moment classification prompt inputs

Provide:

  • Transcript text
  • Neighboring transcript context
  • Visual description
  • Start and end times
  • Asset title
  • Organization vocabulary
  • Controlled marketing taxonomy
  • Language

  • Collection membership

15.3 Query parser

Input:

Customer talking about how easy onboarding was in a vertical video.

Output:

{

  "semantic_query": "customer explaining that onboarding was easy",

  "exact_phrase": null,

  "filters": {

    "orientation": ["vertical"],

    "content_types": ["testimonial"]

  },

  "preferred_modalities": ["speech", "visual"],

  "result_type": "moment"

}

The parser must use a strict schema.

If parsing fails, search the raw query without structured filters.

15.4 Retrieval sources

Run in parallel:

  1. Transcript full-text retrieval
  2. Moment-description full-text retrieval
  3. Transcript vector similarity
  4. Moment vector similarity
  5. Twelve Labs multimodal search
  6. Structured metadata matches

15.5 Fusion

Normalize each source to a comparable range.

Initial score:

0.30 × multimodal video score

0.25 × moment-vector score

0.20 × transcript-vector score

0.15 × lexical score

0.10 × structured-taxonomy score

Adjust by query type:

  • Quoted phrase: prioritize lexical transcript score.
  • Visual wording: prioritize multimodal score.
  • Marketing taxonomy: prioritize structured matches.
  • Filename query: prioritize metadata.

15.7 Search pagination

Use cursor-based pagination.

Do not use offset pagination for vector results.

AI_PROVIDER_MODE=fake

Uses deterministic fixtures for:

  • Transcripts
  • Moments
  • Embeddings
  • Video-provider search
  • Classifications

This mode is required for:

  • CI
  • E2E tests
  • Fast frontend development
  • Offline development

26.2 Live-AI mode

AI_PROVIDER_MODE=live

Uses configured external providers.

The application must clearly display whether development is using fake or live providers.

29. Cost controls

MVP safeguards:

  • Maximum upload size
  • Maximum video duration
  • Organization processing quota
  • Deduplicate by checksum before AI processing
  • Do not reprocess unchanged assets
  • Store analysis version
  • Cache query embeddings
  • Batch embedding requests
  • Use proxies for AI analysis where provider quality permits
  • Record cost estimates per processing job
  • Require explicit admin action for full-library reprocessing

Add a development kill switch:

AI_PROCESSING_ENABLED=false


30. Performance expectations

Initial targets:

  • Library API p95 under 500 ms
  • Search API p95 under 4 seconds, excluding initial cold provider latency
  • Player starts within 3 seconds on a standard connection
  • Status update visible within 5 seconds
  • Asset-list pagination supports at least 10,000 assets per organization
  • Background jobs do not block API workers
  • Search handles at least 100 concurrent requests in load testing before pilot launch

These are engineering targets, not promises to customers.


31. Privacy and security requirements

  • All storage buckets are private.
  • Use short-lived signed URLs.
  • Encrypt provider credentials at the application layer.
  • Separate development and production credentials.
  • Scope Google Drive access as narrowly as practical.
  • Maintain an audit trail for connection creation and deletion.
  • Delete OAuth credentials when a connection is removed.
  • Remove provider-indexed content when an asset is permanently deleted.
  • Make organization deletion a controlled backend process.
  • Document external processors used for AI analysis.
  • Do not use customer content to train internal models during MVP 1.
  • Do not enable cross-customer retrieval or face matching.
  • Preserve original source ownership and location metadata.

33. Definition of MVP 1 complete

MVP 1 is complete only when all of the following are true:

Accounts and tenancy

  • Users can sign up.
  • Users can create organizations.
  • Users can invite team members.
  • Organization data is isolated through tested RLS.

Ingestion

  • Direct upload works.
  • Google Drive folder import works.
  • Duplicate media is detected.
  • Processing status is visible.
  • Failed jobs can be retried.
  • Interrupted jobs resume.

Media intelligence

  • Videos receive proxies and thumbnails.
  • Speech is transcribed with timestamps.
  • Videos are indexed multimodally.
  • Searchable moments are generated.
  • Moments receive marketing classifications.
  • Text embeddings are stored.

Search

  • Natural-language search works.
  • Exact phrase search works.
  • Timestamped results work.
  • Filters work.
  • Match explanations are shown.
  • Search evaluation meets the agreed baseline.
  • Search never crosses organization boundaries.

Activation

  • Users can create collections.
  • Users can save moments.
  • Users can select clip boundaries.
  • Users can export and download an MP4.

Operations

  • CI passes.
  • Production deployment is documented.
  • Monitoring exists.
  • Costs are measurable.
  • Security review is complete.
  • Pilot runbook is complete.
  • Three to five pilot organizations can be onboarded.


34. First vertical-slice objective

Before building the complete MVP, the team should prove the architecture through one vertical slice:

A user uploads one video, the system processes it, the user searches for a concept, and the application opens the relevant timestamp.

The vertical slice must include real components:

  • Real Supabase organization
  • Real RLS
  • Real R2 upload
  • Real Temporal workflow
  • Real FFmpeg proxy
  • Real transcript
  • Real Twelve Labs indexing
  • Real search result
  • Real timestamped playback

Collections, Google Drive and clip export should follow only after this slice works.

Use the following prompt when Codex begins work on the repository:

You are working on MVP 1 of an AI-native searchable media library.


Read these files before changing code:


1. AGENTS.md

2. docs/MVP1_IMPLEMENTATION_PLAN.md

3. Relevant files under docs/architecture/

4. Relevant ADRs under docs/adr/

5. Existing tests and module conventions


The product allows business teams to upload or connect unorganized media,

automatically analyze it and search for exact timestamped moments using natural

language.


Architecture:


- Next.js and TypeScript frontend

- FastAPI and Python backend

- Supabase Postgres, Auth, RLS and pgvector

- Cloudflare R2 for private media

- Temporal for durable workflows

- FFmpeg for media processing

- Twelve Labs for multimodal video indexing and search

- Structured language-model outputs for marketing classification

- A modular monolith with separate web, API and worker applications


Critical constraints:


- Every tenant-owned database row must contain organization_id.

- RLS must remain enabled.

- No cross-organization data access is permitted.

- Never expose service credentials to the frontend.

- Never process large media inside synchronous HTTP handlers.

- Never call external AI providers directly from route handlers.

- All provider calls must go through internal adapters.

- Validate all AI output before persistence.

- Ingestion and persistence must be idempotent.

- External AI-provider indexes are not the canonical data store.

- The canonical searchable entity is a timestamped media_moment.

- Do not introduce microservices, Kubernetes, Kafka, OpenSearch or ClickHouse

  unless an approved architecture decision explicitly requires them.

- Do not perform unrelated refactoring.

- Add tests for every behavioral change.


For each assigned task:


1. Restate the objective.

2. Identify the relevant modules and interfaces.

3. Inspect existing implementation patterns.

4. Propose the smallest coherent change.

5. Implement it.

6. Add unit and integration tests.

7. Run lint, type checks and relevant tests.

8. Update documentation.

9. Report files changed, commands run, results, assumptions and remaining risks.


When requirements conflict, prioritize:


1. Tenant security

2. Data correctness

3. Idempotency and recoverability

4. Interface stability

5. Search quality

6. User experience

7. Implementation speed


Do not claim completion when tests have not been run.


36. Recommended first three assignments

The team should begin with three coordinated tickets.

Member A

Build the Next.js application shell, authentication flow and organization

onboarding using mocked API responses. Establish the frontend design system,

protected-route pattern, API-client boundary and E2E test harness.

Member B

Build the FastAPI foundation, organization schema, membership schema,

authentication validation and RLS policies. Expose organization creation and

membership-read endpoints with isolation tests.

Member C

Build the Temporal worker foundation, R2 storage adapter and FFmpeg media

inspection activity. Create a local fixture workflow that accepts a media path,

runs FFprobe and returns normalized metadata.

The first integration checkpoint occurs when:

  • Member A can create an organization through Member B’s API.
  • Member B can create an asset and initiate a workflow.
  • Member C can inspect the uploaded asset and report its metadata.
  • The frontend displays the asset’s processing state.


37. Product-risk checklist

Review weekly:

Search risk

  • Are results actually useful?
  • Are timestamps accurate?
  • Are transcript results overpowering visual results?
  • Can users explain why a result matched?
  • Are Spanish and English both performing acceptably?

Cost risk

  • What is the AI cost per video hour?
  • What is the storage cost per organization?
  • Are duplicate files being reprocessed?
  • Are failed jobs generating repeated provider charges?

Workflow risk

  • Can jobs recover after interruption?
  • Are provider failures understandable?
  • Can an administrator retry safely?
  • Are partial results duplicated?

Product risk

  • Are users searching or browsing manually?
  • Do users save moments?
  • Do users understand “moment” versus “asset”?
  • Does the product reduce time spent locating footage?
  • Are customers willing to connect their real media libraries?

Security risk

  • Are RLS tests still passing?
  • Are signed URLs short-lived?
  • Are OAuth tokens encrypted?
  • Can logs expose customer content?
  • Can provider IDs be used to bypass authorization?


38. Final implementation principle

Do not optimize MVP 1 for the number of features shipped.

Optimize it for one compelling experience:

A company connects a disorganized media library, describes the moment it
remembers and immediately finds the exact usable footage.

Everything that improves that experience belongs in MVP 1.

Everything else should wait.
